### Goal
Effects are the only place gameplay behaviour lives in code (§6.3). Today only `heal` and `restore_sp` run, through the inventory's own seam, and statuses exist only as data.
Build one server-side **effect runner** that every source uses (consumables now, monster skills now, player skills in T-502, cards and quests later), and a **status system** that applies, stacks, ticks, expires and removes statuses.
Monsters with `skills` start using them. Player skills, skill trees, casting by players and cooldown UI are **T-502**.

### Requirements
1. **One effect runner.** It runs a list of `EffectDef` for a caster, a primary target (an entity or a ground cell) and a skill level, using the instance's injected clock and random source. It's deterministic for a given seed.
   - It supports every v1 type in VOCABULARY.md: `damage`, `heal`, `restore_sp`, `apply_status`, `remove_status`, `modify_stat`, `knockback`, `teleport`, `summon`, `area`.
   - Numbers come from the effect's expressions and `formulas.yaml` with whitelisted variables (§6.2), never C# constants.
   - `damage` goes through `CombatResolver` (element, race, size, refine) and raises the same `DamageDealt`, death and EXP-share path as auto-attacks.
   - `knockback` respects walkability and stops at blocked cells.
   - `teleport` covers the forms the data uses (save point, a cell or map) through the existing warp path.
   - `summon` spawns through the spawner's rules, owned by the caster, with a cap.
   - `area` applies its children to the entities in its shape, with a documented order and a target filter (friendly or hostile, from the skill's `target`).
   - Each effect raises events on the bus (hard rule 7), not calls into other systems.
   - A type the runner doesn't support is a load error, not a runtime refusal.
2. **Statuses.** Apply with a chance and a duration from data; `max_stacks` with a documented refresh or stack rule; `on_apply` modifiers with the source `status:<id>` (§6.1), removed cleanly on expiry, removal or death; `on_tick` effects every `tick_interval_ms` of simulated time, the caster kept for EXP shares and kill credit; `prevents_move`, `prevents_attack` and `prevents_skills` enforced by movement and combat with reason terms; `remove_status` by id or tag. Statuses end on death and don't survive a warp unless you decide otherwise and record why. Tie every timer to the tick clock.
3. **Consumables.** Replace `BasicItemEffects` with the runner, so `item.antidote` and `item.swift_elixir` work (ADR-002 row 171). `unsupported_effect` goes away or is kept only for load-time checks; update VOCABULARY.md.
4. **Monster skills.** Monster AI uses its `skills` entries (chance, level) through the runner, with the skill's range, cast time and cooldown from data, and raises a cast event the client can show. `stats --duel` counts monster skills (row 118); report the wasp's numbers before and after.
5. **Wire and client (§5.4, §10).** Each visible entity's statuses (id, stacks, time left, whether it's a debuff) reach clients in the AOI. Only what a player needs to see; never chances or the caster's numbers. The client shows icons for the own character in the HUD and a compact marker above other characters, plays the status `vfx` key, and shows knockback and teleport as movement. Keep the §9 budgets and the crowd draw-call peak under 100 (row 164), measured with `tools/loadtest --spare-slots` with statuses active; say how you measured.
6. **Tests.** Every effect type, with a seeded random source; status apply, stack, refresh, tick, expire, remove by id and tag, end on death; modifiers on and off; the prevents flags with their reasons; knockback against walls; area targeting; summon cap; the consumables that used to be refused; a monster casting its skill; golden values for one poison tick and one venom sting; the status fields on the wire; a scripted client run step that shows a status on the own character and on a monster.
