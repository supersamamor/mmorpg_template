### Goal
Entities walk. A `MoveTo` intent asks the server to move an entity to a cell; the **movement system**
(an `ITickSystem` from T-202) validates it, computes the path with T-203's `Pathfinder` using the
`balance.yaml` movement limits, and advances the entity every tick with `GridMover` at its `move_speed`.
Stepping onto a warp cell warps the entity. Movement is visible to other systems only through entity state
and events. This is the server half of tap-to-move; AOI (T-204) and the gateway (T-205) come later.

### Requirements
1. **Intents:** `MoveTo(entity, cell)` and `StopMove(entity)`, owned by the movement system. Several `MoveTo`s for the same entity in one
   tick: the last one wins. Validation (rejections are events with a reason term, never exceptions): entity unknown/dead, target out of
   bounds or unwalkable (no "nearest cell" fallback for players in v1), no path / path too long / node limit (`PathStatus`), entity has no
   movement speed. A `MoveTo` to the current cell while idle does nothing.
2. **Path:** computed on the tick from the entity's **current cell** with `Pathfinder` (one instance per system, i.e. per map instance —
   it is not thread-safe) and `PathLimits` built once from `BalanceDef.Movement`. A new `MoveTo` while moving re-paths with
   `GridMover.SetPath` so a step in progress is not lost when the new path continues through the cell being walked to.
3. **Advancing:** every tick, each moving entity advances by `TickContext.DeltaMs` at its `move_speed` (cells per second). Update
   `Entity.Cell` and `Entity.Facing` from the mover. Process entities in a fixed order (entity id) so the result is deterministic.
   Entities do not block each other in v1 — say so in §4.
4. **Speed comes from stats, never from C#:** the system reads `move_speed` (`DerivedStats.MoveSpeed`) from the entity's stat sheet.
   Entities don't have stats yet: add the smallest hook that works (e.g. an optional `StatSheet` on the entity, set by whoever spawns it,
   or an injected speed source) and explain the choice; T-301 (monsters) and T-701/702 (players) will fill it. An entity without a speed
   cannot move (rejected, see 1). Read the speed when a move starts and on each cell reached, not just once, so buffs can apply mid-path.
5. **Warps:** when an entity reaches a cell that has a warp in the map grid (T-201), stop it and request `TickContext.Warp` to the warp's
   target. Only on *arriving* at the cell, not when standing on it or when spawned there. A rejected warp leaves the entity stopped on the
   warp cell (T-202 already raises `WarpRejected`).
6. **Events** (add to `EventNames` + VOCABULARY.md): movement started (with the path length), cell reached (old → new cell, facing),
   movement stopped (reason: arrived / cancelled / warped / rejected-style terms). Keep the reason terms as constants in one vocabulary
   class. Justify per-cell events vs. fewer events in your reply — T-204 will turn them into snapshots.
7. **Tests** (with T-202's test kit and a fake clock, on small `TestGrids` and the sample `map.starter_meadow`):
   orthogonal and diagonal timing at a known speed (arrival tick = expected within one tick); re-path mid-step keeps progress;
   last `MoveTo` in a tick wins; each rejection reason; `StopMove`; no speed → rejected; speed change mid-path takes effect at the next
   cell; walking onto a warp warps (and a rejected warp leaves the entity stopped); spawning on a warp cell does not warp;
   determinism — two instances fed the same intents end in the same cells with the same events; a throwing path query is not possible
   (but a missing grid is a boot error, not a tick error).
8. **Cost:** a test or log that moves e.g. 200 entities across `map.starter_meadow` and records the tick cost (log it, don't assert wall time)
   and allocations per tick after warm-up (assert zero or justify what allocates).
