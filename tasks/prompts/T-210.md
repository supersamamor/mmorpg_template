### Goal
On a phone, connections drop all the time: the app goes to the background, the train enters a tunnel, Wi-Fi switches to 4G.
Today (T-205) the character is despawned the moment its socket ends. After this task the character **stays in the world for a grace
period**, and the app can **resume** it with a **resume token**: same character, same map, a fresh full snapshot, deltas after that —
as ARCHITECTURE §10 describes. A deliberate `logout` still leaves at once. Saving the character on final logout is T-702; leave the seam.

### Requirements
1. **Resume token:** issued in `welcome` (`token`). At least 256 bits from a cryptographically secure RNG, URL-safe encoded. Bound to one
   character. **Single use and rotated:** every successful resume returns a new token in its `welcome` and invalidates the old one. Compare in
   constant time; never log a token (log a short fingerprint at most). Tokens live in server memory only; a server restart invalidates them
   (say so in §10 — T-701 will add durable sessions).
2. **Disconnect → grace period:** when a session ends without `logout` (socket closed, error, idle timeout, `too_slow`), the character is
   **not** despawned: it is stopped (`StopMove`), its view sink is detached, and it stays in the world, visible to others, for
   `grace-period-ms` (a `GatewayOptions` setting, default 60 s, overridable like the other options). When the grace period ends, it is
   despawned (the T-702 save seam goes here). Protocol errors that end the session (`malformed`, `rate_limit`, `update_required`, …) also
   start the grace period — a buggy message must not delete a character instantly — except where you can argue otherwise; explain.
3. **`logout`:** a new client message. The server answers `bye logout`, closes, and despawns the character on the next tick, no grace period.
4. **Resume:** `hello` may carry `resume` (the token) instead of `name`. The server still checks protocol version and content hash (T-209)
   first, then the token. Valid → the new session takes over the same entity, wherever it is now (it may have warped before the drop):
   attach the view, send `welcome` (same entity id, current map, **new** token), then a full snapshot via `RequestSnapshot`, then deltas.
   Unknown, used or expired token → `bye resume_failed` (the client then shows login). Resume works outside development too — it is not
   the dev login — but in this task only characters created by the dev login exist; keep the check in `Login` so T-701 plugs in.
5. **Takeover:** if a resume arrives while the old session is still open (the server hasn't noticed the drop yet), the old one gets
   `bye replaced` and closes, and the new one takes the character. Never two sessions on one character.
6. **Abuse:** count failed resumes per remote address with a small token bucket (config); over it → `bye rate_limit` and refuse further
   resumes for a while. Log failures without the token.
7. **Shutdown:** `bye shutdown` to every session; characters in their grace period are despawned (T-702 save seam), and the server still exits 0.
8. **Docs:** update §10's lifecycle step 6 and message table, and add the **client resume flow** for T-206: keep the token in memory
   (not on disk); on app resume or socket drop, reconnect with backoff and `hello{resume}`; on `bye resume_failed`, go to the login screen;
   on `bye logout`/`replaced`, don't reconnect.
9. **Tests** (with the fake clock; no long sleeps — poll with a timeout): drop → still in the world and visible to another client → resume
   within grace → same id, `welcome` with a new token, full snapshot, deltas continue; the old token no longer works; resume after the grace
   period → `resume_failed` and the character is gone; `logout` → immediate despawn; takeover → old session gets `replaced`; resume after a warp
   lands on the new map; character stops moving when dropped; brute-force resumes → `rate_limit`; shutdown with characters in grace; a token never
   appears in logs (capture the log in a test).
