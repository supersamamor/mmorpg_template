### Goal
Players sign in to a real account and pick a character slot, instead of typing a name into the dev login. Saving what a character *owns or has done* is T-702; this task stores only who exists.

### Requirements
1. **Persistence base.**
   - EF Core with Npgsql, versions in `Directory.Packages.props`. The connection string comes from an environment variable or server option, is never committed and never logged.
   - Tables: accounts, sessions, characters (slot, account, unique name, job id, created, deleted). The character has a permanent id (a GUID) that is separate from the runtime `EntityId`.
   - One migration. The server refuses to start on a missing or newer schema, with a clear message. It applies migrations itself only in development; elsewhere a command does it.
   - Database work never runs on a tick thread.
2. **Accounts.**
   - Username and password only: no email or other personal data (T-703 owns privacy; password reset is a follow-up).
   - Hash passwords with Argon2id from a maintained package: say why that one, and state its parameters. Rehash at login when the parameters change.
   - Normalise usernames, and store and compare the normalised form.
3. **Account endpoints.** HTTPS on the gateway's host: register, login, logout, list characters, create a character, delete a character (soft delete).
   - Cleartext HTTP on loopback in development only, the same rule as `ws://`.
   - Rate-limit per address and per account, with lockout and backoff. The answer and its timing are the same for an unknown user and a wrong password.
   - Bound every request body, and validate every field.
4. **Sessions.**
   - 256-bit random tokens. Only the SHA-256 is stored; they expire, and logout and a password change revoke them. Tokens and passwords never appear in logs.
   - `hello` carries the session token and character id in place of `name`; resume (T-210, T-214) keeps its rules.
   - The dev login stays, in development only.
   - Decide whether resume tokens survive a server restart ("durable sessions", ARCHITECTURE §10), and document it.
5. **Character slots.**
   - The number of slots and the name rules (length, characters) come from `balance.yaml` with validation.
   - Names are unique, case-insensitively, under concurrent creates: the database decides.
   - An account plays one character at a time; a second login follows the existing `bye replaced` rule.
   - Creation takes a name only. Appearance is T-705 and T-706: leave room for it.
6. **Client.**
   - Sign-in, register and character-select screens in T-211's style: 48 dp targets, the words in `UiText`, in the `-Run ui` matrix.
   - The password is never stored on the device. The session token is kept in the platform's secure storage if Godot offers it without native code; if not, memory only. Report which.
   - `TransportPolicy` (T-216) applies to the account endpoints too.
   - The existing e2e runs keep working through the dev login.
7. **Tests.**
   - Every endpoint with every refusal; hashing and rehashing; token expiry and revocation; rate limits with an injected clock; the name race; `hello` with a good, expired, revoked or other account's token.
   - Tests against a real PostgreSQL are in their own category. They are skipped **with a visible reason** when no database is configured, and CI runs them with a service container.
   - Do not use an in-memory EF provider to stand in for PostgreSQL: it doesn't enforce the unique index the name race relies on.
   - One scripted e2e run: register, create a character, enter the world, log out, sign in again.
