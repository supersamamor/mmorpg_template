### Goal
Someone who clones the template can play it on one Windows PC in a few steps: start the server and its database, start the game, register, make a character and play, with two windows to see each other.

### Requirements
1. **Server in a container.** A Dockerfile for `Game.Server` (multi-stage, the pinned .NET, a non-root user, only what the server needs: content and the theme manifests, no client, no tests). The image runs the migrations itself (`--migrate`, then starts) or by the documented command.
2. **Compose.** The server joins `docker-compose.yml` **behind a profile** (for example `play`), so plain `docker compose up -d` still starts only the database as today. The connection string comes from the environment, the database waits for its health check, the port is on loopback only, and the dev password stays a dev password (say so where it is set).
   Decide how the server listens inside a container while still refusing plain `ws://` outside development and anything but loopback in development (the transport rules of ARCHITECTURE §10 stay), and say why. A self-signed certificate made by a script is fine; a committed key is not.
3. **The game on Windows.** A preset and a script (`client/export-windows.ps1` or a mode of an existing one) that builds a Windows desktop build which reaches the local server: a debug build allows `ws://` on loopback; a release build needs `wss://` and a certificate it trusts. Pick one, say why, and never weaken the release rule. Through `Invoke-GodotStep` (§8.5), bounded and retried. The output is gitignored.
4. **One command each.** `play-local.ps1` at the root (or under `tools/`): checks Docker is running (and says so if not, never starts Docker Desktop itself), builds and starts the stack, builds the game if needed, and starts one or two game windows. A `-Stop` that stops only what it started, and a `-Reset` that wipes only the play stack's data after asking. Works in Windows PowerShell 5.1 and PowerShell 7.
5. **Docs.** `README.md` gains a short "Play it on your PC" section; `docs/MOBILE_BUILD.md` or a new `docs/LOCAL_PLAY.md` has the details, the ports, what is a dev secret, and how to change them. Linux and macOS: say what differs, without testing them.
6. **Tests and checks.** A test that the server's options for the container keep the transport rules; the Dockerfile builds; the stack comes up healthy and a scripted client (headless, `run-e2e.ps1` style) registers, makes a character and enters the world against it; then the stack is taken down.
