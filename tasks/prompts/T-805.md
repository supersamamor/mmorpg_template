### Goal
`Game.Admin` (ARCHITECTURE §12.1): a separate ASP.NET Core Blazor Server app where staff sign in and use the admin API: server status, player lookup, a character's saved state, the audit log, and the commands their role allows.

### Requirements
1. **The app.** `src/Game.Admin` (net10.0, Blazor Server, in `Game.sln`), referencing `Game.Shared` (paths, headers, terms) and `Game.Content` (to show item and monster names from content, read-only), never `Game.Server`. Versions in `Directory.Packages.props`. No game rule of its own.
2. **Sign-in.** OIDC with an authorization-code flow (any standard provider, configured by settings: authority, client id, the secret from the environment), MFA left to the provider (say so). Provider groups or claims map to the three roles by configuration. No local passwords. A **development** sign-in for local use only (refused outside Development, and say how it is refused), so the panel can be tried without a provider.
3. **Calling the server.** One typed client that sends the five headers of `docs/ADMIN_API.md` (the service credential from the environment, never logged, never sent to the browser), handles every error term with words, retries nothing that writes, and times out. The server URL and the credential are settings, not code.
4. **Pages.** Status (refreshing on a timer, not faster than every few seconds); accounts and characters search with paging; one account (its characters) and one character (its saved state, with item names from content); the audit log, searchable by target, staff, action and time; commands: kick from a character or account page with a required reason and a confirmation. Every command button is greyed out below its lowest role (from `GET /commands`), and the server's refusal is still shown when it says no. A visible warning near every reason field: no personal data in reasons (STORE_COMPLIANCE).
5. **Security.** Antiforgery, secure cookies, a strict content security policy, no third-party scripts or fonts, HTTPS outside development, the panel itself not reachable from outside unless configured (say what a fork does: VPN or allowlist, §12.2), no secrets in the browser or the logs. Staff id and role come from the sign-in, never from the browser.
6. **Running it.** A `dotnet run` path for local use against a local server with the admin API on (document the settings, including how to point it at the T-807 play stack if that is possible without changing it), and a Dockerfile for the panel (not added to compose: say why or why not).
7. **Docs.** `docs/ADMIN_PANEL.md` (setup with a provider, roles, local use, security notes for a fork); ARCHITECTURE §12 a few lines on what was built.
8. **Tests** in `tests/Game.Tests` (or a new test project in the solution, if bUnit or the like is needed: decide): the client's headers and error handling against a fake server, the role mapping, greyed-out commands, the development sign-in refused outside Development, no secret in any rendered page or log, and one test against a real in-process server with the admin API on that signs in (development sign-in), reads the status and kicks a test player.
