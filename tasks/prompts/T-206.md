### Goal
The first real client in `/client`. A developer starts the server and the client on one PC, and the client:
1. loads the packed client bundle and connects;
2. draws the map from placeholder geometry;
3. walks when the ground is tapped;
4. shows other entities moving smoothly;
5. attacks a tapped monster;
6. shows HP and death, and can respawn;
7. survives a dropped connection.

Real art, theme loading and authored map scenes come later, so everything visual here is a placeholder behind a small seam.

**Risk accepted by the owner:** no phone has run the engine yet. Android and iOS device results are unknown, so **do not claim any device
number**. Say exactly what was measured on desktop and what still needs a phone.

### Requirements
1. **Project.** Use the same Godot version, SDK and framework settings that `docs/MOBILE_BUILD.md` and the spike's csproj pin, with the Mobile renderer and
   landscape. `Game.Shared` is referenced as `netstandard2.1`, with no reflection over it. The client is **not** in `Game.sln`: a plain
   `dotnet build` at the root must not need Godot. Check that root `Directory.Build.props` and `Directory.Packages.props` don't break it, as the spike did.
2. **Pure core, thin Godot layer.** Everything that can be tested goes in `client/Core/**`, with **no `Godot` namespace**, and is linked into
   `Game.Tests`:
   - protocol parsing;
   - the view model (applies snapshots and deltas);
   - interpolation;
   - the connection state machine.

   Godot nodes only read this model and draw it. Time comes in as a parameter.
3. **Protocol.** Reuse `Game.Shared/Protocol`. `src/Game.Server/Net/ProtocolJson.cs` is meant to compile on the client too, so link it if it
   has no server dependencies. If it has any, write the client mapping in `client/Core` and add a test that runs real server output through it,
   and name the dependency in your reply. Unknown fields are ignored. Parsing is on the socket thread; the view model changes on the main thread.
4. **Bundle** (rows 67, 87).
   - An MSBuild or documented step packs `export-client` output into the project. The generated file isn't committed.
   - Commit `content/client-content.reference.json`, so CI's `--check` step starts comparing.
   - The client refuses a `format_version` it doesn't know, with a clear screen, and sends the bundle's hash as `content` in `hello`.
   - `bye update_required` shows an update message.
5. **Connection** (row 66): implement the §10 client resume flow exactly:
   - the token lives in memory only;
   - backoff with jitter;
   - stop once the grace period must be over;
   - every `bye` reason does what §10 says;
   - backgrounding and foregrounding are handled.

   The server URL and dev name come from one client settings file or the command line, defaulting to the dev loopback URL. No secrets in the client.
6. **Map.** Build the ground from the bundle's map width, height and `walkable` / `blocks_los` flags: one batched mesh or MultiMesh, with blocked
   cells visibly different. Cell `(x, y)` → world `(x + 0.5, 0, y + 0.5)` (§4). Reloading on a `map` change works, including a warp. Put this behind a
   seam that T-208's real scenes can replace.
7. **Camera** (row 65).
   - Fixed-pitch 3/4 follow camera. Pinch or scroll wheel zooms within a clamp. All numbers are client config.
   - Measure how many cells are visible at the default zoom at 1280×720 and at a typical phone aspect (19.5:9).
   - Compare with the `aoi.*` comment in `balance.yaml` (~22×13). Entities must not pop in on screen. Report the numbers. Don't change `balance.yaml`; propose a change if one is needed.
8. **Tap input.** One input path for mouse and touch.
   - Ground tap → raycast to the plane → cell → `move`, with an immediate tap marker.
   - Tap a monster → `attack`; choose hit targets generously enough for a 48 dp touch.
   - `rejected` removes the marker or target highlight quietly.
   - The client never checks range, path or walkability as authority.
9. **Entities and interpolation.**
   - Render about 2 ticks behind, using `tick_rate` from `welcome`, and interpolate from `cell` to `next` at `speed` (a diagonal step takes √2 as long).
   - Extrapolate from arrival time within a step, so a walker doesn't stop and start at each cell (row 66).
   - Facing turns smoothly.
   - No prediction of movement or combat.
   - Placeholder shapes differ by `kind` (capsule, sphere, small box for items), and pooled nodes mean no per-frame allocation.
   - Keep the §9 LOD rule in mind: the placeholders stay under budget at 40 entities.
10. **Minimum combat display.**
    - A small HP bar from `hp`; own HP, SP and EXP from `vitals` and `exp`; a one-line flash for `hits`, which T-303 replaces.
    - A monster with `dead` is shown as dead.
    - Ground items are visible; `mine` is highlighted.
    - `you_died` shows a death screen with a respawn button. **The same screen appears when a snapshot after a resume already shows the player dead**
      (row 102): own HP 0 from `vitals`.
    - All display names come from the bundle by `display_key`. Text is never baked in; no ids or numbers from content in C#.
11. **Battery and budgets (§9).** 30 fps cap, no per-frame work when nothing changes, zero allocation per frame after warm-up in the interpolation and draw paths.
12. **Tests** in `tests/Game.Tests/Client/`:
    - snapshot and delta application, including `next:null`, appearing and disappearing in one delta, map change;
    - interpolation timing, including the diagonal √2 and a late delta;
    - the connection state machine, for every `bye` reason and the backoff limits;
    - that the resume token is replaced on every `welcome`, and that nothing writes it to disk;
    - bundle format refusal;
    - a golden parse of real server messages.
