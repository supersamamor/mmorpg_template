### Goal
`dotnet run --project src/Game.Tools -- export-client <out.json>` writes the **client bundle**: the display-only subset of the content
that the app packs (names, descriptions, asset keys, skill targeting info, UI text, map layout), plus a **content hash**. The bundle is a
**whitelist**: only fields deliberately copied into client records get out, so a new secret field on a definition can never leak by accident
(hard rule 11). The server computes the same hash at boot; a client that logs in with a different hash is told **update required** (§5.4).

### Requirements
1. **Whitelist records** in `Game.Shared/ClientContent`, one per definition type the client displays. Include: ids, names, descriptions,
   asset keys (model, icon, scene, music, animation set), item kind / equip slot / weapon type, skill targeting (target kind, range, area shape
   and size, cast time if it is a fixed number — a formula string is server-only), job names and their skill tree layout, status display
   info (name, icon, whether buff or debuff), NPC names and models, dialogue text, quest names / descriptions / objective display text,
   elements and stat ids for labels. For **maps**: id, name, scene key, music key, width, height, the cell flags (walkable / blocks LOS — needed
   for tap-to-move previews with T-203's pathfinder), warps (cell + target map), NPC placements and zones.
2. **Never in the bundle** (write this list in ARCHITECTURE §5.4 too): drop tables and chances, monster stats, AI and spawn data (`spawns`),
   formulas and `balance.yaml`, EXP tables, quest internals beyond display text, hidden/secret flags, the grid's `source_scene_hash`.
   Add a **leak test** that builds the bundle from the sample content and fails if any key or value in the JSON matches a deny list
   (e.g. `drop`, `chance`, `spawn`, `formula`, `ai`, `exp`, `respawn`, monster HP/ATK values) — and a test that a property added to a server
   definition record does not appear in the bundle unless mapped.
3. **Canonical, reproducible output:** stable ordering (by id), invariant culture, fixed number formatting, UTF-8 without BOM, `\n` line endings.
   `export-client` run twice gives byte-identical files on any OS. The **content hash** is SHA-256 over the canonical bundle bytes (excluding
   the hash field itself), hex lowercase; write it into the file and print it. A `--check <file>` mode exits non-zero if the file is stale.
4. **Format version:** the bundle has a `format_version` (start at 1). The client will refuse unknown versions — say so in §5.4.
5. **Handshake (the only `Net/**` change):** `hello` gains an optional `content` (the client's bundle hash); `welcome` gains `content` (the
   server's hash). The server computes its hash at boot with the same builder. If the client sends a hash and it differs → `bye` with a new reason
   `update_required` and close. If the client omits it: allowed in development (log a warning), refused outside development (`update_required`).
   Old fields keep their meaning; bump nothing else. Update ARCHITECTURE §10's message table.
6. **Default output** `build/client-content.json` (gitignored); the path is an argument. Don't commit a generated bundle.
7. **Tests:** golden-shape test for a small fixture bundle; reproducibility (build twice → identical bytes and hash); the leak tests in 2;
   `--check` passes on a fresh export and fails after a content edit; hash changes when any displayed field changes and **does not** change when
   only server-only data changes (e.g. a drop chance or a monster stat) — so balance hotfixes don't force an app update; gateway: matching hash
   → welcome with `content`, mismatch → `bye update_required`, missing hash in development → accepted, outside development → refused.
