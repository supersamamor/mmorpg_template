### Goal
The server boots, loads and validates content, creates one **map instance** per map, and runs a
deterministic **10 Hz tick loop**: drain queued intents → run the ordered systems → dispatch the
tick's events on the **event bus**. Entities can enter, leave and warp between instances. Nothing
moves yet and nothing is networked: this task builds the frame that movement (T-203/T-212),
AOI (T-204), the gateway (T-205) and spawns (T-301) plug into.

### Requirements
1. **Tick phases** (document them in ARCHITECTURE §3): per instance, per tick:
   1. drain the intent queue (intents enqueued since the last tick, in arrival order);
   2. run the systems in a fixed, registered order (`ITickSystem` with `Tick(TickContext)`), each seeing the intents routed to it;
   3. apply deferred structural changes (entity add/remove, warp hand-offs) — never mid-system;
   4. dispatch the events raised this tick, in raise order.
   An exception in a system is logged with the instance, tick number and system name; it must not kill the loop or other instances.
2. **Determinism:** the simulation core (instance + systems + bus) takes `IClock` and `IRandom` (the existing PCG32) by injection
   and does no I/O. The same intents fed into the same tick numbers give the same state and events — prove it with a test that runs
   two instances side by side and compares. Tick number and simulated time come from the loop, not the wall clock.
3. **Scheduler:** fixed 10 Hz (100 ms; the rate is a locked decision, keep it a named constant in one place). Use a monotonic clock,
   compensate drift (schedule against the start time, not "sleep 100 ms"), and when overrun, catch up at most a few ticks then skip
   with a logged warning rather than spiral. Record per-tick duration (min/avg/max over a window) and log it periodically.
   Instances tick independently (one long instance must not delay the others); choose the threading model and explain it.
4. **Intent queue:** thread-safe enqueue from any thread (the future gateway), single-reader drain on the tick. Intents are
   immutable records with the target entity id; unknown or dead entity → dropped and counted, not thrown. Bound the queue per
   instance and say what happens when full.
5. **Entities:** an instance owns its entities. Entity ids are unique per server run, allocated by the world, never reused in a run.
   Minimum state now: id, kind (player/monster/npc), map id, cell, facing. Keep it a plain data layout systems can extend later —
   explain the choice (components vs. classes) briefly; don't build a full ECS.
6. **Warps:** a `Warp` request moves an entity to another instance (or another cell on the same map) at the end of the tick:
   it leaves the source instance, then enters the target on the target's next tick. Raise enter/leave events. The target cell must be
   walkable on the target's `MapGrid` (from T-201); otherwise reject and keep the entity where it was.
7. **Event bus:** typed publish/subscribe (`Publish<T>`, `Subscribe<T>`), per instance, synchronous dispatch in phase 4. A handler
   that publishes queues for the next tick (no re-entrant dispatch). Systems never call each other — they talk through intents and events
   (hard rule 7). Event names are `EventNames` terms; add any new ones (e.g. entity entered/left map) to VOCABULARY.md.
8. **Boot:** `Program.cs` loads content from a path (argument or default `content/`), validates it and refuses to start on errors
   (print them like `validate` does), creates the instances, runs until Ctrl+C, then stops cleanly (finish the current tick, stop the
   loop, exit 0). No network listener yet.
9. **Tests** (with a fake clock that you advance by hand): phase order; deferred add/remove; warp to another instance, warp to an
   unwalkable cell rejected; events dispatched in raise order and next-tick for nested publishes; a throwing system doesn't stop the
   tick; queue bound; determinism (2); scheduler drift/catch-up logic tested without real sleeping.
