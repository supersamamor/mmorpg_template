### Goal
A character's looks are chosen once, at creation, checked and stored by the server, and sent to everyone who sees the character. Drawing them, and the creation screen, are T-706.

### Requirements
1. **Creation.** `POST /account/characters` takes an optional appearance: gender, skin tone, face, hairstyle, hair colour. The server checks every id against `appearance.yaml`, and that the face and hairstyle belong to the gender. A bad one is refused with an "Account errors" term, and nothing is created. Left out, the gender's or file's defaults apply: document which gender a request without one gets, and why.
2. **Storage.** Ids only, with the character, in one transaction with its creation. Characters that exist already get the defaults, by a documented rule in the migration or at load. The migration holds no content id that a fork would have to edit.
3. **Content changes.** An id removed from `appearance.yaml` falls back to that gender's default at load, is logged once per character, and is not overwritten in the database: putting the option back restores the look.
4. **In the world.** The appearance sits on the player's entity and follows warps. It is immutable while in the world, and cosmetic only: no rule reads it. The dev login gets the defaults.
5. **On the wire.** A few ids in the view record of `snapshot` and `appeared` entries; deltas never repeat it. Measure the bytes per player before and after, and what a full crowd adds. If the ids cost too much, propose an index into the bundle's lists instead, but keep the content hash check in mind.
6. **The character list** (`GET /account/characters`) returns it too, so a select screen can draw it.
7. **Client data only.** `client/Core/**` reads the new fields into its entity and character models, and ignores an id its bundle doesn't have. Nothing is drawn differently yet.
8. **Room for T-708** (cosmetic outfits): say how outfit slots would travel beside this without changing these fields.
9. **Tests.** Every refusal; the gender rules; defaults; the round trip through real PostgreSQL (T-701's `DatabaseFact`); the migration on a database with characters; content removal and return; snapshot and appeared, but never delta; a hostile client's ids; the dev login.
