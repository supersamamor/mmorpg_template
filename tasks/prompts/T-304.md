### Goal
The **data side** of ARCHITECTURE §7.8: content can name sounds for monsters, items and maps (all optional); the theme's
`asset-manifest.json` can give a sound several variations, a volume, a pitch range and a bus, plus **category defaults**
(`audio.defaults`) and **event sounds** (`audio.events`); `validate` checks all of it; and the client bundle carries the sound keys.
The aim is that any sound can be replaced by editing one manifest line or file. Nothing plays yet — the client audio system is T-305.

### Requirements
1. **Content fields (all optional, asset keys only):** `MonsterDef.sounds` with `aggro`, `hit`, `die` (`sfx.*`); `ItemDef` `use_sfx`, `equip_sfx`;
   `MapDef` `ambience_asset_key` (`ambience.*`). Skills already have `sfx_asset_key`. Weapon-type swing/impact sounds are **not** content
   fields: weapon types are vocabulary, so they map in the manifest's `audio.defaults` (requirement 3). Explain any other choice.
2. **Manifest sound entries** (`sfx.*`, `ambience.*`, `music.*`): accept the existing `{ "file": ... }` and a richer form:
   `files` (one is picked at random), `volume_db`, `pitch` `[min, max]`, `bus` (an audio bus term), `loop`. Document the shape in §8.
3. **`audio.defaults`:** category → sound key, for `monster.aggro|hit|die`, `item.use|equip`, `weapon.<weapon_type>.swing|impact`, and
   `ui.tap|open|close|error`. **`audio.events`:** `EventNames` term → sound key (e.g. `LevelUp`, `QuestCompleted`, `ItemAcquired`).
   Fallback order the client will use (write it in §7.8): content key → category default → silence.
4. **Validation** (errors name the file and path, like the other rules): every sound key referenced by content, defaults or events exists in
   the manifest with the right prefix; categories and event names are known terms (`weapon.<type>` uses `WeaponTypes`); bus is a known
   term; `pitch` min ≤ max and both > 0; `volume_db` within a sane range you document; every listed file ends in `.ogg`; `files` not empty.
   A missing optional content key is **not** an error.
5. **Client bundle:** add the content sound keys to the bundle records (monsters, items, maps). The manifest stays a theme file (not in the
   bundle). Re-run the leak tests; sound keys must not trip them (adjust the deny list only if a sound key name collides, and say so).
6. **Samples:** give each sample monster `sounds`, a couple of items `use_sfx` / `equip_sfx`, both maps an ambience, a full `audio.defaults`
   (including every weapon type in VOCABULARY) and `audio.events` for at least `LevelUp`, `JobLevelUp`, `QuestCompleted`, `ItemAcquired`.
   Point them at placeholder files like the existing entries, and show one entry using the rich form with variations.
7. **Tests:** each validation error; the rich and simple manifest forms both parse; defaults and events resolve; a content key overrides
   nothing at load (resolution is a client concern, but add a small pure `AudioResolver` in `Game.Shared` that implements the fallback order
   so T-305 and tests share it); bundle includes the sound keys; schemas regenerated.
