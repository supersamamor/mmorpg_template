### Goal
A client can connect to the server over a WebSocket, log in with a **dev-only login stub**, appear on the starting map, send
**move/stop intents**, and receive its **full snapshot** and then **per-tick deltas** from T-204 — and two clients see each other walk.
The **message contracts** live in `Game.Shared` so the Godot client (T-206) uses the same types. JSON on the wire (MessagePack later if
measured traffic needs it, §10). Resume tokens, the background grace period and reconnect are **T-210**; real accounts and auth are **T-701**;
the content-hash check is **T-209** — leave clear seams for them, don't build them.

### Requirements
1. **Contracts (`Game.Shared/Protocol`):** a small envelope with a message type name (VOCABULARY terms) and a protocol version sent in the first
   message. Client → server: `hello` (protocol version, dev display name), `move` (target cell), `stop`, `ping`. Server → client: `welcome` (your
   entity id, map id, server tick rate), `snapshot`, `delta` (mirroring T-204's `ViewSnapshot`/`ViewDelta`), `rejected` (intent rejected, with the
   reason term from `MoveRejected`), `pong`, `bye` (close reason). Keep field names short but readable; document the JSON shape in ARCHITECTURE §10.
   Contracts carry only display data (hard rule 11). Serialization must not need runtime reflection on the client: keep the JSON mapping in
   `Game.Server/Net` (System.Text.Json source generation is fine), or explain how the client will serialize the same shapes AOT-safely.
2. **Host:** Kestrel WebSockets on a configurable port and path. `ws://` only on loopback in development; outside development require TLS
   (`wss://`) with a configured certificate and refuse to start without one. Ports, paths, limits and timeouts are **server config** (options with
   defaults, overridable from the command line/env), not game content — keep them in one options type.
3. **Session lifecycle:** connect → `hello` within a timeout → **dev login stub** (no password; only enabled in development, refused otherwise) →
   the player entity is created on the instance tick through a thread-safe entry point → `welcome`, then a full snapshot via `RequestSnapshot` →
   deltas. On close, error, or timeout, the entity is removed on the next tick (T-210 will add a grace period here — mark the seam).
   Wrong protocol version, malformed JSON, unknown type, oversize message (cap it), or a message before `hello` → `bye` with a reason and close.
4. **New character (data, not code):** add a `new_character` block to `BalanceDef` / `balance.yaml`: start map id, start cell, start job id.
   Validate at load (map exists, cell walkable on its grid, job exists). The player gets a `StatSheet` built from content (starting stat values +
   the job, as the stats pipeline already does — reuse `Game.Content` helpers rather than re-deriving) so it has a `move_speed`. Its
   `DefinitionId`/display key is the job id. No ids or numbers in C#.
5. **Inbound:** parse on the socket thread, validate shape and bounds (cell inside the map), map to intents (`MoveTo`, `StopMove`), and enqueue on
   the instance's queue. **Rate-limit per session** (§11) with a token bucket from config; over the limit → drop and count, persistent abuse → `bye`.
   The client never sends results; a `move` is a request the movement system may still reject (→ `rejected`).
6. **Outbound / back-pressure:** the `IViewSink` is called on the tick thread and must not block it (T-204 contract): copy or serialize there and
   hand off to a per-session bounded send queue drained by the socket. If a client falls behind (queue full), drop its pending deltas and send a
   fresh snapshot when it catches up instead of an ever-growing backlog; a client that stays behind is disconnected. Measure and report the
   per-tick cost of the sink on the tick thread.
7. **Warps:** when the player warps, its session follows it to the target instance (inbound goes to the new instance's queue; the warp's full snapshot
   from T-204 arrives on the new map) — `welcome`-style "map changed" info is part of the snapshot or a small message, your call.
8. **Tests:** contract JSON round-trips (golden JSON for each message type); an in-process host on a random loopback port with `ClientWebSocket`:
   hello → welcome → snapshot; move → deltas show the walk; **two clients see each other appear, walk and disappear**; each `bye` reason (timeout,
   bad version, malformed, oversize, before hello, rate limit); dev login refused outside development; slow-reader back-pressure → resync snapshot;
   disconnect removes the entity; warp moves the session. Use a fake clock where timing matters; no fixed sleeps longer than needed — poll with a timeout.
9. **Measure:** with ~50 connected loopback clients walking, log real bytes/s per client on the wire (vs. §9's 10 KB/s) and the tick-thread cost of
   the sinks. Log, don't assert wall time.
