### Goal
Pure, deterministic grid movement primitives in `Game.Shared/World`, built on T-201's `MapGrid`:
an 8-direction **A\*** pathfinder, a **line-of-sight** test, and a **grid mover** that advances an
entity along a path over time at `move_speed`. No tick loop, no networking: T-212 wires these into
the server's tick loop (T-202). They live in `Game.Shared` so the client can use the same rules
for tap-to-move previews — the server stays authoritative.

### Requirements
1. **Directions:** helpers between the 8 `Directions` terms and `(dx, dy)` steps, using T-201's axis convention
   (`+x` east, `+y` south). Facing from one cell to another (including non-adjacent: the nearest of the 8).
2. **A\***: `FindPath(MapGrid, start, goal, …)` → the cells to walk (excluding start, including goal), or "no path".
   - 8 neighbours; a diagonal only if both orthogonal neighbours are walkable (no corner cutting).
   - Cost 1 orthogonal, √2 diagonal; octile heuristic. Paths must be optimal under these costs.
   - **Deterministic**: a fixed neighbour order and a fixed tie-break, so the same query always gives the same path on every platform
     (no floating-point ties that flip between runtimes — e.g. compare with integer costs 10/14 or a fixed epsilon; explain the choice).
   - Bounded: stop after a max number of expanded nodes and reject paths longer than the max path length (5). Return a clear reason.
   - Unwalkable goal: option to path to the nearest reachable walkable cell around it (needed for "attack that monster" later), off by default.
   - Allocation-light: reusable per-thread or caller-owned search buffers sized to the grid; no per-node allocation. Measure it.
3. **Line of sight:** `HasLineOfSight(MapGrid, from, to)` over cells flagged `blocks_los`, symmetric (`a→b == b→a`), endpoints don't block.
   Pick a supercover or Bresenham variant, document how it treats lines passing exactly through a corner, and test that case.
   Also `ChebyshevDistance` and `InRange(from, to, range)` helpers (ranges are in cells, Chebyshev — §4).
4. **Grid mover:** a small value-type state machine: given a path, a `move_speed` (cells/second) and elapsed milliseconds, advance the
   current cell, the fractional progress to the next cell and the facing. A diagonal step takes √2 times as long. Leftover time carries into
   the next step (moving at 10 Hz must give the same arrival time as moving in one big step, to within one tick). Stop, re-path (replace the
   path keeping the current cell), and "arrived" are explicit. It never checks walkability itself — the path is already validated.
5. **Limits come from data:** add a `movement` block to `BalanceDef` / `balance.yaml` with the max path length (cells) and the max nodes
   expanded per search, with comments. Validate both are > 0. Regenerate schemas. No movement number in C#.
6. **Tests:** straight, diagonal, around a wall, no corner cutting, no path, goal unwalkable (both modes), max length and node limits,
   optimal cost against a brute-force BFS/Dijkstra on small random grids (seeded `Pcg32Random`), determinism (same path twice, and the
   golden path on the sample `map.starter_meadow` grid committed as an expected list), LOS cases incl. corners and symmetry, mover timing
   (orthogonal vs diagonal, 10 Hz steps vs one step, re-path mid-step).
7. **Budget:** a test or benchmark that runs a worst-case search on the largest sample map and logs the time and allocations
   (assert zero allocations after warm-up; log the time, don't assert it — wall clock flakes under parallel test runs).
