### Goal
A developer changes content and sees it in the running game within seconds, without restarting the server; and someone who does not want to hand-edit YAML can change common content in a small local editor that never writes anything invalid.

### Requirements
1. **Hot-reload, development only.** A server option (off by default) watches `content/` (and the theme's manifest if it matters). On a change it loads and validates the **whole** set in the background (every rule, every cross-reference: rule 5); a set with any error is refused, logged with the errors, and the running content stays. A valid set is swapped in **between ticks**, all at once. Release builds and any server whose transport is not loopback refuse the option at start (say how, test it).
2. **What a swap does to the world**: decide and state it per kind. For example, new numbers apply from the next tick; monsters and NPCs whose definitions changed or vanished are respawned; a player's items whose definitions vanished are refused at load as today rather than deleted. Nothing in the database is rewritten by a reload. Say what cannot hot-reload in v1 (maps' grids, for example) and log it plainly when such a file changes.
3. **Clients**: development clients are told the display bundle changed (one message; the bundle hash is what changes) and fetch and apply it, or show "content changed, reconnect" if applying live is too much for v1 (decide). The bundle still holds only display data (§5.4, rule 11).
4. **Editor**: a local tool (for example `dotnet run --project src/Game.Tools -- editor`) serving a small web page on loopback only, for the common kinds (items, monsters, skills, NPC dialogue lines, shop lists, quest texts: choose a useful first set and say why). Forms are driven by the generated JSON Schemas, not hand-written per field; ids are namespaced and picked from existing ones where they are references; every save validates the whole set first and writes nothing if it fails, showing the errors. Writes keep the YAML files' comments and order where the library allows (say what it loses); one file per save, atomically. No authentication beyond loopback; it refuses to bind anything else. Original names only in examples.
5. **No game content in code** (rule 2): the editor knows kinds from the schemas, not from C# lists of fields.
6. **Docs**: ARCHITECTURE (hot-reload and the editor), a short `docs/CONTENT_EDITING.md` (start the editor, what reloads live and what does not), VOCABULARY for any new term, ADR-002 rows from 500.
7. **Tests**: a reload with a valid change swaps between ticks; an invalid change is refused and nothing changes; a vanished monster definition respawns or removes as decided; release and non-loopback refuse the option; the editor's save refuses an invalid set and writes nothing, writes atomically, keeps what you said it keeps; it binds loopback only. One e2e run: a development server with hot-reload, a client playing; a content file's display name changes and the client shows the new one (or the reconnect message, as decided).
