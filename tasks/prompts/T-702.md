### Goal
An account's character comes back as it left: level, EXP, points, stats, skills, job, quests, inventory, worn equipment, cards, refine levels, currency, save point, map and cell, HP and SP. A crash may lose the last moments, but it never duplicates or splits an item or currency.

### Requirements
1. **What is saved.** List every piece of per-character state in the code and decide for each whether it is saved, with the reason: statuses, cooldowns (row 214), autopilot (T-604) and open dialogue included. Content is never in the database: save ids and numbers only.
2. **The tables.** Migrations on T-701's base. Item instances have permanent unique ids, enforced by the database (dupe audits, §11). Give the id source a design that no restart can repeat (`NextEntryId` restarts today).
3. **One transaction per save.** A character's whole state is saved together, with a version number, so an older save can never overwrite a newer one. Two servers, or a late save, must not both win.
4. **Never on a tick thread.** The tick takes a consistent snapshot of the state; the database work runs elsewhere. Say what a snapshot costs per character, and measure 100.
5. **When it saves:** on an interval (server option), on a map change, on logout, at the end of the grace period, when the account switches characters, and on shutdown. Shutdown waits for the saves within a bound, and reports any that failed.
6. **Items between characters.** An item dropped by one player and picked up by another, with different save times, must not exist twice after a crash. Choose an ordering (or save them together) so that a crash loses rather than duplicates. Document it, and prove it with a fault-injection test that kills the save at every step. T-903 (trade) will build on this.
7. **Loading.** Loaded before the character enters the world. Validate against the current content: a removed item, skill, quest, job, map or a now-blocked cell is handled by a documented rule (kept aside, refunded or moved to the start), logged, and never a crash or a silent deletion.
8. **Failure.** If a load fails, the login is refused with a reason, and nothing is created or overwritten. If a save fails, retry with backoff and keep playing; say when the character is at risk, and what a player sees. A character whose last save hasn't landed cannot be logged in again from older state.
9. **Deleted characters** (row 289): re-check on entering the world, so a deleted character does not stay playable.
10. **Row 264** (a turn-in asked while warping): settle it now.
11. **Dev login** characters stay in memory only, and the server runs without a database in development as today.
12. **Tests.** Round trips of every field; the version rule; fault injection; content changes between save and load; concurrent login and save; shutdown; a crash mid-save; tick time unaffected. Tests against real PostgreSQL where the database decides something, following T-701's `DatabaseFact`. One e2e run: play, change several kinds of state, restart the server, and find it all back.
