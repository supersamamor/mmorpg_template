### Goal
A player can delete their account and its data from inside the app, and a fork has what the stores ask about privacy. Sign in with Apple is **not** built: Apple asks for it only when another third-party login is offered, and the template has none; say so where a fork would look.

### Requirements
1. **Deletion request.** Signed in, current password again, and a second confirmation in the client (say what is lost). The same guards, limits and log rules as a password change (T-710).
2. **What it does.** At once: every session ends with the game played on it (T-710), the account can no longer sign in, its characters cannot be entered or seen by name. After a waiting time (server configuration; default 14 days; 0 allowed) the data is erased for good. Signing in during the wait offers to cancel, and nothing else.
3. **Erasing.** One transaction per account: account, sessions, characters, states and items. Decide what happens to character names (T-701 keeps a deleted character's name taken) and say why; nothing left behind may identify the person. Runs on the server in the background, never on a tick thread, bounded per pass, safe when two servers do it at once and when the process dies in the middle, and never while a live server holds a character.
   A character's last save after the request must not bring anything back.
4. **Support and law.** A record that a deletion happened, holding no personal data (when asked, when done, the account id), for support and for restoring a backup: describe in the docs how a restored backup is cleaned again.
5. **Export.** Not built here (T-806 has the export queue); the docs list what data is held, why and for how long, so a fork can answer.
6. **Store files.** Documented in `docs/STORE_COMPLIANCE.md`, in plain words for a fork owner: the Play data-safety answers and the iOS privacy manifest entries for what the template does today (checked against the code, each with the file that shows it), a privacy-policy outline marked as needing the fork's own lawyer, the web page for deletion requests that Play asks for (what it must say; the template ships none), age rating notes, and what changes when a fork adds analytics, ads, crash reporting or purchases.
   If the pinned Godot's iOS export can carry a privacy manifest from settings, set the template's; otherwise say how.
   Check current store rules on the web, with links and the date read; if a rule cannot be confirmed, say so instead of guessing.
7. **Client.** In the account panel: delete account (password, what is lost, confirm), the waiting state with cancel, every refusal in words. 48 dp, safe area, text scale to 1.5, the new screens in the `ui` matrix with 0 problems. Passwords are cleared as T-710 does.
8. **Tests.** Every rule above: service, endpoints, real database (races: login, save, claim, second server, crash between steps; erasing leaves no row and no name but what you decided), gateway (the game ends), the client flow. The `account` e2e run gains delete, cancel and delete again on a throw-away account.
