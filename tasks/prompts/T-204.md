### Goal
Every **observer** entity (a player; later maybe a spectator/GM) gets, each tick, exactly what changed among the entities **near it**:
which appeared, which moved or turned, which disappeared. On demand (entering a map, resuming after a disconnect) it gets a
**full snapshot** of what it can see. Visibility uses an **AOI grid** so the cost scales with what is nearby, not with the map.
This is still transport-free: the output goes to a per-observer **view sink** interface that the WebSocket gateway (T-205) will
implement and serialize. The client (T-206) renders ~2 ticks behind and interpolates (§10), so a delta must carry enough to
interpolate a walk without sending every intermediate position twice.

### Requirements
1. **Phase 5 — outbound**, after phase 4 (events), as ARCHITECTURE §3's "events → AOI diff" says: the instance's final state for this tick
   (after structural changes) is diffed per observer and handed to its sink. Update the §3 phase list. Phases 1–4 keep their behavior,
   and the T-202/T-212 tests must still pass unchanged.
2. **AOI grid:** the map is divided into square AOI buckets of `aoi.bucket_size` grid cells; an observer sees every entity whose bucket is within
   `aoi.view_radius` buckets of its own (Chebyshev). Keep buckets up to date incrementally from entity add/remove/cell changes (the movement
   events from T-212 and the enter/leave events from T-202, or a direct hook in phase 5 — your call, explain it). No O(entities × observers)
   scan per tick. An observer always sees itself.
3. **What a client sees per entity** (the view record): entity id, kind, a **display key** (the content id the client looks up in its display
   bundle — e.g. a monster or NPC id; add a nullable `DefinitionId` to `Entity` if needed), cell, facing, and movement: the next cell and the
   current speed while walking, so the client can interpolate between ticks. Nothing the client must not know (§11 / hard rule 11: no AI state,
   no HP of others yet, no paths beyond the next cell, no spawn data). Write down in the reply why each field is there.
4. **Numbers from data:** add an `aoi` block to `BalanceDef` / `balance.yaml` (`bucket_size`, `view_radius`, with comments; validated > 0).
   Pick values so a phone in landscape with the fixed 3/4 camera (§7.2) sees a bit past the screen edge on the sample maps; say how you chose them.
5. **Deltas:** per observer per tick, one message with: `appeared` (full view records), `changed` (only entities whose cell, facing or movement
   changed — only the changed fields if you can keep it simple, otherwise the whole record; justify), `disappeared` (ids). Nothing when nothing
   changed (battery budget §9: no per-tick work on an idle client). Deterministic order (entity id). An entity that crosses a bucket boundary
   into view appears, out of view disappears; warping out disappears for everyone, and the warping observer gets a fresh full snapshot on the target map.
6. **Full snapshot:** `RequestSnapshot(observer)` (an intent or a direct call on the instance tick — must run on the tick thread) sends the full
   visible set and resets that observer's baseline. Needed for map entry and resume (§10).
7. **View sink:** an interface the gateway will implement (`IViewSink` or similar). It is called on the instance's tick thread and must not
   block it: document that implementations copy/serialize and queue, never do I/O inline. A sink that throws is logged and detached, not fatal.
8. **Tests:** appear/move/disappear across bucket boundaries; observer sees itself; no message when idle; `changed` only lists real changes;
   warp out/in (disappear for old neighbours, appear for new, full snapshot for the warper); full snapshot resets the baseline;
   two observers with overlapping views; a throwing sink; determinism (two instances, same intents → identical message sequences);
   the T-202/T-212 tests unchanged.
9. **Budget check (§9: ≤ 10 KB/s per client with 50 visible entities):** a test with ~50 walkers visible to one observer (and a few hundred
   elsewhere on the map) serializes the messages with System.Text.Json in a test helper (not the T-205 wire format, which doesn't exist yet) and
   logs bytes/second per observer. Also log the outbound-phase cost with ~500 entities and ~100 observers, and allocations per tick. Log, don't
   assert wall time. If JSON is over budget, say so and what you would change — don't switch formats in this task.
