### Goal
The server has the admin API of ARCHITECTURE §12: a private, authenticated HTTP listener where staff tools (the panel, T-805) read server state and send admin commands that go through the game like player intents, each one checked against the staff member's role and written to an append-only audit log. T-806 adds the moderation and support commands on top; this task builds the road and drives one command down it.

### Requirements
1. **Listener.** A second Kestrel listener, separate from the game's: its own address and port, loopback by default, off unless configured, never on the game port or path. Outside development it needs TLS and refuses to start without it or on a public address unless an option says the network is private (say how a fork runs it behind a VPN or allowlist). Bounded bodies and time, `no-store`, nothing served but the API.
2. **Who is calling.** A service credential (a secret from the environment, never logged or committed, compared in constant time) proves the caller is the panel. The staff member arrives with each request: id, display name and role (`support`, `gm`, `admin`, vocabulary). Decide how the server trusts what the panel says about the staff member: §12.2 wants the panel to do OIDC; say what the server checks itself and what it must take from the panel, and why. Unknown or missing role: refused. Rate-limited per credential.
3. **Admin commands.** A generic command type that is queued into the tick loop of the right instance (or handled off-tick where it does not touch the world) and validated there like an intent; the result goes back to the caller (accepted, refused with a term, or the outcome). Role is re-checked on the server for every command; a table of command to lowest role, in one place, tested. A required free-text reason on every write.
4. **Audit log.** Append-only table, same transaction as the change (rule 10) where the change is in the database, and before the answer where it is not: staff id, role, action, target, before and after (as JSON), reason, time, request id. The database role the server uses cannot update or delete audit rows, or say what enforces it in this template (trigger, rules, grants) and test it. Personal data in the log follows docs/STORE_COMPLIANCE.md: say what erasing an account does to its audit rows, and update that document.
5. **Reads.** Server status (players online, instances, tick p50/p99 and max, saves, error counts, the loaded content hash with `ClientBundleExporter.Hash`, rows 50 and 74); account and character lookup by name or id (paged, never a password hash or token); one character's saved state; the audit log, searchable by target, staff and time.
6. **The first command: kick.** `support` and above: ends the account's live game (as T-710's session end does: saved, resume token dead) with a new `bye` reason; the client says so and goes to the sign-in screen. Audited.
7. **Events.** Admin actions are published on the event bus (rule 7) so later systems can react.
8. **Docs.** ARCHITECTURE §12 gains what was built and decided; VOCABULARY the new terms; a short `docs/ADMIN_API.md` with every endpoint and how to call it locally (curl), and how T-805 and T-806 build on it.
9. **Tests** for every rule: listener options and refusals, credential and role checks (constant time where it matters), rate limit, every endpoint's shape and bounds, the role table, audit rows written with the change and never editable (real database), kick end to end with the gateway, nothing secret in any log. One e2e run: a scripted client plays, an admin call kicks it, the client shows it and the audit row is there.
